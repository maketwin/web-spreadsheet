# 规模与性能

web-spreadsheet 的网格是 Excel 的地址空间：**1,048,576 行 × 16,384 列**（A–XFD，唯一定义在 `src/util/gridSize.ts`）。支撑这个规模的核心原则是**地址空间不是分配**——键是一个数字，任何代价只能随「已存储的单元格数 / 元数据条数」走，不能随选区或已用范围的面积走。

## 这条原则怎么落地

- **存储稀疏**（`src/store/SheetData.ts`）：格子以数值键 `r * TOTAL_COLS + c` 存在一张 Map 里；遍历走已存储格子（`forEachCell` / `forEachCellInRect`），统计走 `getCellCount` / `getUsedBounds`，见[数据模型](/guide/data-model)。
- **结构操作整体搬移**（`src/store/Store.ts`）：插删行走 `insertRows` 等原语，半平面一次移完、只发一个 `structure` 事件，撤销只保留被删的格子等轻量载荷，见[命令与撤销](/guide/commands)。
- **清空同样整体处理**（`Store.takeCellsInRect`）：选中整列按 Delete 是一次扫描加一个 `cells` 事件，撤销用 `bulkSetCells` 一次放回；公式同步层对超过 256 个位置的批量改写按外接矩形处理，只看住在里面或读到里面的公式，代价与被清空的格子数无关。
- **大区间稀疏求值**（`src/formula/`）：超过稠密上限的区间按已存储格子精确聚合，见[公式引擎](/guide/formulas)。
- **导入导出只逐个处理已存储格子**（`src/io/`），极稀疏的形状走「稠密打包 + 坐标还原」，见[文件 I/O 与持久化](/guide/io)。
- **自动保存分片编码**（`src/db/`）：按表标脏、每片约 20,000 格、片间让出主线程。

## 上限常量

| 常量 | 值 | 语义 |
|------|-----|------|
| `MAX_MATERIALIZED_CELLS` | 250,000 | 一次粘贴平铺 / 填充最多写入的格子数（粘贴只在锚点落一次，填充到该数为止） |
| `MAX_DENSE_RANGE_CELLS` | 2,000,000 | 一个区间引用最多读进一个稠密数组的格子数；更大的区间仍精确（聚合走已存储格子，其余函数返回 `#VALUE!`） |
| `MAX_HISTORY_RETAINED_CELLS` | 2,000,000 | 撤销历史按保留单元格数的内存预算，超限淘汰最旧的撤销步 |
| `RANGE_DEP_CELLS` | 256 | 超过它的大区间登记成一个矩形依赖而不是每格一条边 |
| `MAX_DENSE_EXPORT_EMPTY_CELLS` | 1,000,000 | xlsx 导出的内部调优常量：已用范围里的空地址超过它走稀疏打包路径 |

前两个从 `web-spreadsheet` 与 `web-spreadsheet/core` 两个入口导出（`src/util/limits.ts`）。

## 实验台

仓库内可复跑，数字不必口口相传：

```bash
pnpm bench:scale         # Node 基准：store / 多表 / 公式 / 导入导出
                         # （test/scale/*.bench.ts，结果写 coverage/scale-bench/*.json）
pnpm e2e:scale          # 真实浏览器：e2e/scale.spec.ts 量「到屏幕」时间与主线程最长阻塞（独立的 Playwright 配置，不在 `pnpm e2e` 里）
```

### 真实浏览器（无头 Chromium，开发构建）

一百万格的单表（100,000 × 10）与 50 张表的工作簿，量的是「到屏幕」的时间与主线程最长一次阻塞（相邻两帧的最大间隔；60 Hz 下不掉帧即 ≤ 17 ms）：

| 操作 | 单表 100 万格 | 50 张表 |
|------|---------------|---------|
| 打开工作簿到屏幕 | 2.2 s | 1.7 s |
| 刷新页面后从 IndexedDB 恢复 | 1.2 s | — |
| 滚动 300 格滚轮 | 16.8 ms | — |
| 跳到 XFD1048576 / 在那里输入并提交 | 16.7 ms / 33 ms | — |
| 选中 A 列设为粗体 | 33 ms | — |
| 表头右键在第 4 行上方插一行 / 撤销 | 267 ms / 233 ms | — |
| 选中 A 列按 Delete / 撤销 | 567 ms / 400 ms | — |
| 编辑后空闲 7 秒（自动保存） | 16.8 ms，没有长任务 | — |
| 切换工作表（4 次里最差的一次） | — | 17 ms |

另外两项单独量的结果：100 万格在回收后的活跃堆约 60 MB（约 60 字节/格）；自动保存改动前每次都有一个约 260 ms 的主线程长任务，改动后用真实的 `startAutoSave` 测了 3 次保存（全量、大表改一格、小表改一格），都没有 ≥ 50 ms 的任务。

## 仍然较慢的操作与已知限制

如实列出当前的已知慢点（数字见上表）：

- **百万格的 xlsx 导入导出需数秒**，在 Worker 里进行（界面不冻结），导入内存峰值约 1.1–1.4 GB；
- **50 万行 × 3 列排序 1.3–3.1 s**，撤销 1.5–2.0 s；
- **一次改动触发多个百万格聚合时，每个聚合约 65 ms**；
- **选中数十万行设样式约 0.3 s**——每行一条元数据是数据模型决定的；
- **200 张表 × 25 万条公式**：录入 8.9 s、全量重算 8.1 s、带着公式引擎重新载入 10.1 s，Node 堆约 1.9 GB。同样的操作在 50 张表 × 10 万条公式时是 1.7 s / 0.85 s / 1.5 s——增长是超线性的，原因尚未定位；
- **溢出数组（`SEQUENCE` 等）不能原样通过 xlsx 往返**：导出把锚点公式和溢出值写成了各自独立的单元格，读回后锚点看到被占用的邻居而显示 `#SPILL!`。这是原有的缺口，与网格规模无关。
